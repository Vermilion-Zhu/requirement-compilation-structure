## 0. 一页结论（可做封面/摘要）

- 项目目标：把 ARC-Bench 的 `requirements.yaml` + Given/When/Then + 参考图，自动编译成可部署的
  React + Express + SQLite 应用，并尽量通过平台的隐藏外部测试。
- 我们经历了两次架构：
  1. **十三阶段需求编译器**（staged）：逐层产出 schema → 读写义务 → API → UI IR → trigger → 验收，
     每层各自生成、检查、修复；
  2. **轻量 ReAct 引擎**（Lite）：先把需求编译成来源关联的完整契约，独立生成并冻结浏览器测试，
     再由一个持续会话完成跨层实现，`verify` 把构建/启动/浏览器失败直接回灌。
- 关键收获：外部测试考的是"用户按需求走完整流程"，内部测试考的是"各层产物是否自洽"；
  两者之间的语义缺口（可访问名、地标、入口页、跨阶段数据流）才是通过率的主要瓶颈。
- 当前状态：`bookstack` 分支已合并两条线，支持 staged 与 react 两个 engine；
  合并后 **400 个测试通过（53 skipped）**；Lite 候选版本 `0.1.0a3` 等待平台送测。

## 1. 项目背景与目标

### 1.1 任务

ARC-Bench 给一个需求目录（`requirements.yaml`、验收场景、参考图），要求 Agent：

- 入口固定：`python3 main.py <需求目录> --output-dir <应用根>`；
- 生成可直接部署的 Web 应用（`deploy.sh`、`HOST/PORT`、构建与启动）；
- 平台用**外部测试**（我们看不到）验证真实用户流程；
- 平台还会看运行状态、追溯信息与合理性。

### 1.2 约束

- 模型只通过 `OPENAI_BASE_URL` / `OPENAI_API_KEY` / `MODEL` 注入，不能写死；
- 平台运行时间有限（早期任务可达数小时，Lite 设 900 秒量级预算）；
- 我们无法调整提交后的参数，**默认值就是最终行为**；
- 隐藏外部测试的定位方式（role/name、地标、路由）与内部测试不同构。

### 1.3 成功标准

1. 能稳定生成并启动应用；
2. 外部测试通过率尽可能高；
3. 单任务耗时/模型调用可控；
4. 方法对不同任务（Keep、BookStack、StackOverflow…）可迁移。

## 2. 初始架构：十三阶段需求编译器

| 阶段 | 产出 | 内部验证 |
| --- | --- | --- |
| 00–01 | 工程脚手架、需求树、参考图分析 | 输入快照 + 容错 |
| 02–05 | DB schema、读写义务 Ω、SQL、种子数据 | schema/义务检查、真实 DB 启动 |
| 06–08 | API 契约（I/O/R/W/P/Q）、后端实现 | HTTP TDD |
| 09–11 | UI/数据 IR、页面实现、trigger 设计 | UI 存在性测试 |
| 12 | 交互实现、E2E、独立验收 | Playwright 真实浏览器 |

设计意图：把"需求 → 数据 → 接口 → 界面 → 交互"拆成可检查的中间契约，每层失败可局部修复。
实际运行后发现两个问题：

1. **串行往返多**：每个阶段都要模型生成 + 检查 + 修复，跨层修改要等前一层稳定；
2. **内部测试粒度与外部测试不同构**：内部按 UI/trigger/API 测，外部按用户流程测；
   结果是内部全绿、外部仍可能整片失败。

## 3. 开发历史（从完成整合到当前）

### 3.1 阶段 A：首次可提交（2026-11-04）

**目标**：让整合后的编译器真的能在 ARC-Bench 上跑起来。

| 改动 | 解决的问题 |
| --- | --- |
| 13 个 pass 下沉到 `infrastructure/stages/passes/` + `PASS_MODULES` 注册表 | 入口只存在于根目录教学脚本，ZIP 少带一个就全崩 |
| 00 阶段 baseline 分类 + 受控接管 | 平台预注入的 `backend/frontend` 与模板混装，`npm run build` 必挂 |
| `deploy.sh` 支持 `HOST/PORT`、已安装时跳过 npm install | 平台启动契约 |
| 退出码分级（0/1/130/2）、`--type` 与 `ARCBENCH_*` 兜底 | 平台无法区分"部分完成"和"什么都没产出" |
| 模型参数降级（不强制 `max_completion_tokens` / `response_format`） | 端点拒绝任一参数就 13 个 pass 全 FAILED |

**结果**：首次提交，BookStack 外部 **3/12**。
**教训**：能提交 ≠ 能通过；外部测试从第一步就在考"用户能不能完成流程"。

### 3.2 阶段 B：稳健性与可观测性（11-04 ~ 11-05）

| 改动 | 解决的问题 |
| --- | --- |
| 输入容错：先落需求快照，缺失图片/材料只告警；需求树缺 ID/类型异常可归一化 | 一张图缺失导致 02–12 连锁失败 |
| `runtime_events` 适配层 + 七张追溯表 | 网站上看不到逐需求状态与契约 |
| 契约可视化：API/页面/trigger/测试行写入 traceability | `interfaces`、`tests` 长期为空 |
| 47 条陈旧测试分类：修复 9 条、46 条 legacy 门控 | 长期红着的测试掩盖真实回归 |
| `scripts/analyze_log.py` | 把一次性日志分析变成可复用工具 |

**结果**：BookStack 外部 **4/12**（含 E2E 复用实验的版本）。
**教训**：基础设施稳定后，瓶颈开始转向"语义是否正确"。

### 3.3 阶段 C：外部测试驱动的语义对齐（11-05 ~ 11-13）

这是 staged 架构的主要改进期。按问题类型归纳：

#### C1 运行时质量：E2E 复用与可诊断性

- 每次 E2E 都重新拉起 Vite + 后端；第 12 阶段 377 s 花在启动上。
- 改为"每个应用只起一对服务器并跨多次复用"，后端源码指纹变化才重启；
- 真实产物本地复现后又修了四处：Vite 相对路径、`.arc` 未建即写日志、复用已删除的临时目录、
  runner 后端未回收；runner 改为**完全静默**（stdout 留给 Playwright JSON）。
- 结果：E2E 单次耗时从约 199 s 回落到 20 s 量级（含 180 s 空等的 bug 修复后）。

#### C2 数据义务账本（D1）

- 字段级读写义务散落在 `db_obligations`、API、trigger、验收报告里，无法回答"这条义务履行了吗"。
- 新增 `.arc/obligations.json`：稳定 `OBL-*` ID、需求/步骤归属、`api`/`trigger` 分配者、
  `Inferred → Allocated → Verified → Implemented` 状态与测试证据；
- 纯投影、不改门禁，失败只告警。

#### C3 语义 IR：role / name / state

外部测试按 `getByRole(button, {name:'Edit'})` 这类可访问性定位；内部测试用 `data-testid`，
所以"Edit 写成 `<a>`"内部完全发现不了。

- UI 元素新增 `role`（必填）与 `name`（可访问名≠可见文字时）；
- 规则按**行为**判定：改变数据/当前记录、提交/保存/取消/删除/打开编辑器 → button；
  只在阅读流里切换视图 → link；记录集合 → 带名字的 region；
- 实现阶段按声明的 role 渲染，不再"看哪个标签顺手"；
- 后来补充：`status`/`alert` 区分、`aria-pressed/current/expanded` 状态绑定、
  `{var}` 动态名称模板、设计告警的一次修复回合。

#### C4 应用壳（Application Shell）

- 导航被当成"首页的一部分"，导致部分页面没有导航；外部 `go('Books')` 要求每页都有
  `navigation` 地标 + Books 链接。
- IR 新增 `scope: global | page`：壳元素 `parent=null`、跨需求复用、页面子树不含壳；
- 实现阶段在应用入口渲染一次并包裹所有路由；
- 回归：某轮把面包屑也建模成 `navigation`，出现两个含 Books 链接的 nav，
  外部 `getByRole('navigation')` strict mode 失败，BookStack 从 11/12 掉到 3/11。
- 修复：提示词禁止页面级第二导航地标 + `semantic_issues` 报告"页面 navigation 重复壳链接名"；
  `pre-m4` 检查点回退后重放，BookStack 回到 **12/12**。

#### C5 依赖与等待预算（M1/M2）

- 模板 `tailwindcss: ^4.0.0` 在平台镜像解析到 4.3.5，而 `@tailwindcss/oxide@4.3.5` 不存在：
  6 次 ETARGET、阶段 05 762 s、12 轮编辑；
- 锁定已验证的 4.3.4；安装失败带 npm 输出尾部；同一 manifest 失败不再重试；
- E2E 生成提示词要求 5–8 s 显式等待，失败不再每个用例烧满 30 s。

#### C6 入口路由与命名地标（M8/M9）

StackOverflow 9/27，18 条失败全是 10 s 超时。本地构建产物探针发现：

1. `/` 只有占位 `Home`，没有 Question feed（设计里根本没有 route `/` 页面）；
2. 需求写 "Main navigation"，应用是 "Primary navigation"；
3. 需求 "Follow Questions in Main navigation"，应用把 Questions 渲染成 link，外部按 button 找。

对应改动：入口路由必须是真实页面；命名地标逐字保留；导航项"需求称 link 才用 link，
否则 button"；从需求文本抽取 `"X"(role=Y)`、定点 navigation、Follow-in-navigation 角色做校验；
M10 进一步做了**提交前语义探针**（构建产物 + 真实浏览器 + requirement 契约）。

#### 阶段 C 结果

外部测试的逐轮数字、失败构成和归因见 [提交数据分析](submission-data-analysis.md)。这里只保留历史结论：
语义 IR/应用壳把 BookStack 从 3/12 推到 11/12，导航守卫后 12/12；M8/M9/M10 的 Keep 轮外部 7/11，
4 条超时已定位到一次 502 导致的空设计与导航命名回归。

### 3.4 阶段 D：轻量 ReAct 架构实验（11-14 ~ 11-15）

#### 动机

- staged 一轮 13 个阶段、每个阶段多轮模型调用；StackOverflow 一轮 **19068 s**、535 次调用；
- 阶段 08（3179 s）和 12（8460 s）反复"生成—检查—修复"，大量时间花在串行往返；
- 外部测试考的是完整用户流程，逐层产物自洽并不等于流程可用。

#### 新架构

```
requirements.yaml + 场景 + 参考图
        │
        ▼
来源关联的完整需求契约（原文/未知字段/UI 声明/图片索引/指纹）
        │
        ├── 独立生成结构化测试计划（分批，保留完整背景）
        │        └── 校验 → 编译 Playwright → 收集 → 冻结
        ▼
单会话 ReAct 实现（跨层批量编辑：DB + API + 页面 + 交互）
        │
        ▼
verify：构建 + 临时服务 + 每例私有数据库 + 浏览器执行
        │
        ├── 失败 → 观测结果回到同一会话
        └── 通过 → 应用 + 验收证据 + 轨迹
```

关键模块：`infrastructure/react_agent/`（requirements、test_plan、acceptance、submission、
runner、verification、tools、browser_tools、provenance）。

入口：`main.py` 支持 `--engine staged|react`，默认从 `agent-release.json` 读取，否则 staged；
打包器 `scripts/package.py --engine react` 生成 Lite 送测包。

#### 结果

Lite 与 staged 的耗时/通过率对照、平台提交分数和版本趋势，统一放在
[提交数据分析](submission-data-analysis.md)；本节只保留架构层面的结论：
单会话 ReAct 显著缩短了生成时间，但测试表达力和长任务预算仍需继续验证。

#### 新暴露的问题

- 结构化测试计划的表达力（动态 status、相对数值、合法替代分支）；
- 唯一值/邮箱格式等测试数据生成会反向影响模型行为（曾导致模型放宽应用校验）；
- 动态 status 曾被隐式要求包含可访问名称；
- 全页同名标题、Score 等作用域问题；
- StackOverflow 在 900 s 内无法完成（长任务预算与循环裁剪仍需实验）。

## 6. 经验与反思

1. **通过率瓶颈不在"功能有没有写"，而在"语义契约有没有传对"**：
   role/name、地标名、入口路由、导航项角色，这些内部 testid 测试看不到。
2. **软失败必须可观测**：E2E 复用失败曾被 `stdio: "ignore"` 藏住，导致 27 次空等 180 s；
   后来所有旁路输出走文件/stderr，并加"快速失败 + 一次失败即停用"。
3. **回归可能来自"更正确的语义"**：面包屑用 `<nav>` 语义上没错，但外部 helper 假设只有一个
   含 Books 链接的 navigation；这提醒我们"以评测契约为准，语义正确性要服从定位契约"。
4. **内部测试的粒度决定它能发现什么**：逐层产物测试适合定位，但不覆盖用户流程；
   Lite 用"独立冻结的浏览器验收"直接对齐外部行为，是更接近目标的测试形态。
5. **架构不是越"重"越好**：13 阶段提供了可检查的中间契约，但串行往返与跨层修改成本高；
   Lite 用单会话 + 跨层批量编辑显著缩短时间，代价是测试表达力与调试粒度需要新的工具补足。
6. **测量条件必须固定**：不同轮次的模型、提示词、外部套件版本不同，速度/通过率不能直接横比；
   中期报告需要明确口径。

## 8. 5 分钟 PPT 逐页提纲（约 9 页）

> 每页给一句"结论句" + 图表/要点；时间合计约 5:00。

### Slide 1（0:20）标题与一句话结论

- 标题：**从需求编译到轻量 ReAct：一个 ARC-Bench Web Agent 的迭代**
- 副标题：十三阶段编译器 → 单会话实现 + 冻结浏览器验收
- 结论句：*"我们最大的收获不是写完了功能，而是发现并补上了内部测试与外部用户流程之间的语义缺口。"*
- 底部：组名/成员/日期

### Slide 2（0:30）任务与约束

- ARC-Bench：需求 + 场景 + 参考图 → 可部署 Web 应用；隐藏外部测试。
- 约束：入口/部署契约、模型注入、时间预算、默认参数即最终行为。
- 图：一张"输入 → Agent → 应用 → 外部测试"的流程示意。

### Slide 3（0:35）初始架构：十三阶段编译器

- 数据层 → 后端 API → UI IR → trigger → E2E；每层生成/检查/修复。
- 优点：中间契约清晰、失败可定位。
- 代价：串行往返多；StackOverflow 一轮 19068 s、535 次调用。
- 图：13 阶段流水线（可用 README 的 mermaid 简化）。

### Slide 4（0:45）问题：内部全绿，外部整片红

- 例 1：BookStack 首版内部全绿、外部 3/12；Edit 被写成 `<a>`，外部按 button 找。
- 例 2：导航只出现在部分页面，外部 `go('Books')` 从详情页开始就失败。
- 例 3：StackOverflow `/` 没有 feed、导航名/角色不符，18 条 10 s 超时。
- 结论句：*"内部测试测的是产物自洽，外部测试测的是用户流程。"*

### Slide 5（0:50）改进：语义 IR、应用壳与预检

- role/name/state、`scope: global`、命名地标、导航角色规则。
- 回归案例：面包屑成了第二个 navigation → 3/11；守卫 + 回退重放 → 12/12。
- 预检：从需求抽取契约，构建产物上跑真实浏览器。
- 图：BookStack 通过率趋势（需注明用例数变化）。

### Slide 6（0:50）转折：轻量 ReAct 架构

- 完整需求契约 + 独立冻结测试 + 单会话跨层实现 + verify 回灌。
- 时间/通过率数据见[提交数据分析](submission-data-analysis.md)；这里讲架构动机与代价。
- 结果：Keep 与 BookStack Lite 都出现过 11/11、12/12 的外部成绩（版本口径见分析）。
- 图：staged vs Lite 时间对比（同条件数据待补）。

### Slide 7（0:40）结果总表

- 用[提交数据分析](submission-data-analysis.md)中的表格/趋势图，不在这里重复数字。
- 标注：不同轮次测试版本/模型不同，数字不可直接横比。
- 高亮：staged 的 12/12 与 Lite 的 12/12 是两条线的代表性成绩。

### Slide 8（0:30）经验与反思

- 语义契约优先于"看起来正确"的 HTML。
- 软失败要可观测；回归可能来自更"正确"的语义。
- 测试粒度决定发现问题的能力；架构选择是速度/可调试性的权衡。
